# Settings

Status: **shipped; a kit since 01/10/2026** (kits programme step 1, app-factory#1). The operator, verbatim: "this is all stuff that needs to be defined in the settings page of Cadmus so that it's stuff that can be changed by me as the operator without having to come into the backend code... whatever you do will be useful for Godswood and Pebblestone, and all the rest of the apps that use the app factory." Consolidated from cadmus, godswood, pebblestone and master-orchestrator (29/09/2026).

## Decision

**The factory gains a `settings` slice: domain code declares a typed setting where it already lives, one table holds overrides, one table holds an append-only change log, and one admin-gated pair of routes serves both a JSON Schema and the effective values to `@poodle64/ui`'s existing `<SchemaForm>` — which renders the whole page with no per-app frontend code.** It ships as a kit, not stamped files: the backend is `app_slices.settings` (`kits/python/app-slices`), the page `@poodle64/ui/settings`. An app MOUNTS it (`api/main.py` includes `settings.router(...)`, `db/registry.py` imports its models, the settings route renders `<SettingsPage />`), CONFIGURES it through that router's arguments (its session, the caller, the read and write gates), and ADDS settings in its own `api/<domain>/settings.py`. A setting is a typed default in code plus the operator's override in the app's own database; that is application data, not the "declaration" `core.md`'s configuration rule governs (host/URL/port/credential-name facts stay in `config/`, untouched by this). Cost is about 480 lines of backend (the slice ~340, the migration ~70, the mount ~70) and 140 of frontend (one settings destination, one page, no widgets) — smaller than alerts because the rendering engine already exists (`@poodle64/ui/schema-form`, `settings-shell`) and this slice supplies it a document rather than hand-building controls.

```text
domain module (e.g. api/fat_controller/) ──declare_setting(...)──┐
                                                                  ▼
                              app_slices.settings.discover (finds each api/<domain>/settings.py)
                                                                  │
                          GET /api/settings/ (schema + values) ▼   PATCH .../{key}  POST .../{key}/reset
                                                          setting_overrides (effective value)
                                                          setting_changes   (append-only audit)
                                                                  ▲
domain code / a scheduled job / a script ──settings.get_value(session, "key")── (read fresh, every call, no cache)
```

## Shape

- **Declared where the value is used**, exactly like `db/registry.py`'s per-model pattern: a domain module calls `declare_setting(...)` at import time; `settings.router(domains=api, ...)` imports every domain's `api/<domain>/settings.py` (`discover`), found by that name rather than listed, so the admin route can enumerate them all and adding or deleting a domain (the scaffold's `api/example/` included) never edits a list — never a single file that also holds the values or the domain logic.
- **`Setting`** (`app_slices.settings`): `key` (dotted, e.g. `fat_controller.stage_models.triage`), `type` (`boolean | integer | number | string | model_alias`), `default`, `title`, `description`, `minimum`/`maximum` (numeric types), `choices` (closed string set), and for `model_alias` only: `list_models` (a zero-arg callable the app wires to its own gateway's `GET /v1/models` — no field exists for a URL or a key, so a declaration cannot smuggle either) and `narrow` (an app-supplied `alias -> error message | None`, godswood's `refuse_tier1_alias` wrapped to return a message instead of raising). There is no `secret` or `identifier` `SettingType` — the closed enum is the first refusal, by construction.
- **Refused at declaration, not by convention.** `declare_setting` checks `key`, `title` and `description` against a small denylist (`secret`, `token`, `password`, `credential`, `api_key`, `mailbox`, `recipient`, `private_key`, `email`, `phone`) and raises `ValueError` at import time — the app fails to start rather than shipping the field. The list is a backstop for the mechanically-detectable shapes, named as exactly that in its own docstring: a genuinely person-identifying setting with no such string in its name (a free-text "sender name") is still a review-time judgement call, the same one `db/registry.py`'s three-bucket classification already asks of every new table.
- **One row per overridden key**, not one row per declared key: `setting_overrides(key PK, value jsonb, updated_at, updated_by_id)`. A key with no row is running its code default — the common case for most of an app's declared settings, so the table stays small and a declaration ships with nothing to seed.
- **Append-only history**, `setting_changes(id PK, key, old_value jsonb, new_value jsonb, changed_by_id, changed_at)`. A reset is a new row recording new_value = the default, never a delete or a rewrite of an earlier row — satisfies pebblestone's ISO 9001 7.5.3 need for who/when/old/new, readable by an admin, with no destructive path.
- **One accessor, read fresh.** `settings.get_value(session, key)`: look up the declared `Setting`, read `setting_overrides` for that key, return the override or the code default. No module-level cache, no read-at-import, no `lru_cache` — the read happens on the session passed in, so godswood's five gunicorn workers and pebblestone's in-worker scheduler each see a write the instant it commits, with no restart and no cross-process invalidation to build. This is the one place `db/session.py`'s commit-before-response fix (2026.9.50) matters beyond its own route: a write through `PATCH /api/settings/{key}` must be visible to the very next read, including one from a different worker process, which is exactly the ordering that fix landed for.
- **Gated through the admin router's existing dependency**, not a new entitlement: the app mounts the router with `read=module_dependency("admin")` on every route and `write=module_dependency("admin", write=True)` on each mutating one — the identical calls `api/admin/router.py` already makes — and with its own `get_session` and `get_current_user`, so a change is recorded against the caller on the request's one session. The kit holds no gate or identity of its own. An app that has not yet taken the factory's entitlement-based admin gate (pebblestone, on `portal_users.access_tier` until `pebblestone#760` step 4) swaps that one dependency when it converges; nothing in this slice hardcodes a second gate for it to carry alongside.
- **App-wide scope only.** `setting_overrides`/`setting_changes` are `WORKSPACE_EXEMPT` in `db/registry.py`, in the same bucket as `Alert`: no per-workspace division, read and written under the reserved `admin` entitlement. A domain register with its own per-user or per-workspace values (pebblestone's `delegation_limits`) is not a setting and is untouched.

## The page

`GET /api/settings/` returns a JSON Schema (one `object` property per declared setting: `type`, `title`, `description`, `minimum`/`maximum`, `enum` for `choices` or a `model_alias`'s live-fetched alias list) alongside the current effective values and their declared defaults — not a separately-carried "overridden" set, which keys differ is derivable from those two alone, and the frontend derives it rather than the two ever risking disagreement. **No UI Schema is sent.** `<SchemaForm>` reads a `.` in a property name as a path, and the keys are dotted, so the page nests the flat schema and values by dot path and derives the layout from that schema, one group per domain and one Control per setting (`@poodle64/ui/settings`' `nestSchema`, `nestValues`, `settingsLayout`): every declared setting is still laid out with no hand-written layout, and the form's own dispatch table already maps `boolean → switch`, `integer`/`number` (with `minimum`/`maximum`) `→ number`, and a `string` with `enum` `→ select` with zero hints. That is the whole reason constraint 6 ("an app adds a setting without writing UI") is true by construction rather than by a factory-authored widget: the page is a fetch, a `<SchemaForm>`, and a small "overridden from default" panel beneath it listing each changed key with its default and a one-click reset (`POST /{key}/reset`) — `<SchemaForm>` itself has no per-field reset affordance, so that panel is the one bit of page-specific code.

- `frontend/src/routes/settings/+layout.svelte` — the factory's rendering of `SettingsShell` (`sveltekit-frontend.md`'s named settings destination): one group, "This deployment", shown only when `auth.can('admin')`, with one item, "Application". An app adding a personal or workspace settings group later extends the same `sections` array — not built speculatively here, since nothing needs it yet.
- `frontend/src/routes/settings/application/+page.svelte` — mounts `<SettingsPage />` from `@poodle64/ui/settings`: the fetch, `<SchemaForm>` and the overrides panel. Every `onChange` PATCHes the one field that changed and refetches nothing else; a refusal (a 422 on bounds, choices or a refused `model_alias`, a 403 without write) puts the value back and toasts the server's `message`.

## Model alias

`model_alias` is one `SettingType` among five, not the point of the slice — the operator's own framing, 29/09/2026: this is app settings in general ("a well-worn path"), and model choice is only the commonest example. It is a `string` under the hood; the factory stores the bare alias (`<peer>/<what>`) and nothing else. `list_models` is how a declaration reaches "reachable by the app's own gateway key": a zero-arg callable the declaring app writes as a two-line lambda closing over its own settings (godswood: `lambda: gateway_models.list_gateway_models(get_settings().integrations.litellm_url, get_settings().integrations.litellm_virtual_key)`), never a factory-held URL or key. `app_slices.settings.list_gateway_models` is one generic helper — the OpenAI-compatible `GET {base_url}/models` over httpx, which every stamp already carries, returning `[]` with a logged warning on failure, the same shape as godswood's own `list_available_models` — so four apps stop hand-rolling the same 15 lines. The model manifest (`operators/poodle64/registries/registry-models.md`) is never read here: validity is "does the gateway answer with this alias right now."

**`narrow` filters what is offered, not only what is accepted.** Pebblestone's data-tier policy pins document-reading work to Tier 3; a page that shows every gateway alias and only refuses a Tier-1 one on save is inviting the policy breach it then blocks. `build_schema` runs every reachable alias through `narrow` before it becomes an `enum` choice, so a setting an app has narrowed never displays a value it would refuse — `narrow` is one function, read twice, not two mechanisms to keep in sync.

**An unreachable gateway degrades; it never refuses.** `list_models` failing (network error, proxy down) is indistinguishable, to both `build_schema` and `set_value`, from "cannot confirm reachability right now" — the field keeps its current value, is not marked invalid, still accepts a write, and carries a one-line warning in its description. Only a gateway that DID answer, and did not list the alias, makes it invalid — the same soft-fail godswood's own `PUT /admin/fat-controller/stage-models/{stage}` already does (`admin_routes.py`). Refusing on a failed lookup would lock every `model_alias` setting on every app for the length of one gateway restart. `narrow` runs after the reachability check (when it ran at all), for an app-specific privacy or tier rule (godswood refusing a Tier-1 alias); the factory ships no default narrowing, because "any reachable alias is fine" is correct until an app states otherwise.

## Adoption

- **godswood** retires `fc_stage_models` and `settings/stage_models.py` for two declared settings, `fat_controller.stage_models.triage` and `fat_controller.stage_models.job`, both `model_alias`, `narrow=refuse_tier1_alias` adapted to return a message. The five numeric knobs in the ranked inventory (both stage time budgets, placing's grace and floor, the entity auto-match bar, triage's auto-proceed bar, triage's page count) become `integer` settings with the bounds already implicit in their code (a floor and a ceiling declared as `minimum`/`maximum`). The Nextcloud-write-access filing count (`godswood#841`) is declared as a setting from the day that feature lands, per the amendment. Its Setup page (`fat-controller/setup/`) is replaced by `/settings/application`; its read-only admin config page (`admin/config/`) stays — system diagnostics, not operator-settable state.
- **earworm**'s `app_settings` (bare `key`/`value` text, no declaration, no bounds, no history) is the shape this slice generalises: earworm's one row (backfill progress) is process state, not an operator-facing setting, and stays where it is — a raw key-value table with no UI is a different thing from a declared, bounded, admin-editable setting, and folding the two would force process bookkeeping through admin validation it does not need.
- **cadmus** declares its extraction, screen and reviewer models as three `model_alias` settings in whichever module already names them today.
- **pebblestone** declares its extraction cost guards (`dispatch_enabled`, `monthly_ceiling_aud`, `alert_threshold`, `spike_multiplier`, `worker_batch_size`), Peggy's filing-confidence thresholds, its rollout switches (Xero, SafetyCulture, email ingest, the digest/report jobs), and its `mimir/deep`/`titan/fast` model choices, each `narrow`ed to the aliases its data-tier policy admits a document-reading role to reach. A threshold whose own code comments require a `peggy_backtest` run before it moves carries that precondition in the setting's `description`, which is free text — no separate mechanism needed. `delegation_limits` (`api/admin/models/delegation_limits.py`) stays a domain register, per-director not app-wide, and is the closest existing precedent for updated-by attribution this slice generalises; `system_config`'s one live JSONB key retires into a declared setting on convergence. Vector-store schema (collection names, embedding dimension) and encryption keys are never declared — the mechanism is opt-in, so a value nobody calls `declare_setting` on is simply not a setting, and a deploy-only field needs no annotation to stay one.
- **The factory's own `agent.py`** (`timeout_seconds`, `effort`, `haiku_model`) is a plausible future migration — none are start-and-connect facts — but is not moved here: it is a live `config/sections/` file every stamped app already depends on, and converting it is its own change, reviewed on its own, not a side effect of landing the mechanism.

## Rejected

- **A single JSON blob setting** (`app_settings.value: jsonb` keyed by an app-chosen schema, no per-key declaration). Rejected because it reintroduces exactly what earworm's table already shows the cost of: no bounds, no type, no forbidden-kind check, and a page that cannot be generated because there is no schema to generate it from.
- **A per-app settings UI.** The entire point of routing through `<SchemaForm>` is that no app writes one; a hand-built page for even one app's settings is the drift this design exists to end before it starts.
- **Caching the effective value** (in-process, Redis, or read-once-at-import). Rejected outright by constraint 3: five gunicorn workers and an in-worker scheduler must see a write with no restart, and a cache is one more thing to invalidate across processes for a value that costs one indexed `SELECT` to read.
- **A central cross-app settings registry or model manifest as a runtime source.** Explicitly out of scope ("build nothing central"); each app's declarations live in that app's own repo, and `model_alias` reachability is asked of the live gateway, never a shared document.
